# Вопросы тимлида по проекту Seller API (с краткими ответами)

## 1. Два одинаковых POST с одним `Idempotency-Key` пришли одновременно. Как вы гарантируете, что операция выполнится один раз?

Первый запрос атомарно захватывает ключ командой `SET key owner NX EX 30` (scope = merchant + sha256 ключа). Второй не получает lock и либо находит уже сохранённый ответ и отдаёт его как replay, либо получает `409` с `Retry-After`. Чтобы не было гонки «второй получил lock сразу после того, как первый закончил», порядок такой: **сначала сохраняем ответ, потом освобождаем lock**, а после захвата lock ответ перечитывается (double-check). Lock снимается Lua-скриптом compare-and-delete, чтобы не удалить чужой lock после истечения TTL. Fingerprint (method + path + query + body) ловит повторное использование ключа с другим телом (`422`). Сохраняются только 2xx: неуспешные запросы не имели побочных эффектов, поэтому их можно повторять. Корректность проверена `scripts/concurrency-check.sh` на реальном параллелизме (30 параллельных запросов → 1 созданный товар).

## 2. Почему списание остатков — один SQL-запрос, а не `find()` → изменить → `flush()` через ORM?

Read-modify-write теряет обновления и допускает овербукинг: два запроса прочитали 10, оба списали 8. `UPDATE … SET quantity = quantity + :delta WHERE … AND quantity + :delta >= 0 RETURNING quantity` атомарен: PostgreSQL сериализует писателей одной строки блокировкой, условие в `WHERE` — инвариант, `CHECK (quantity >= 0)` — последний рубеж. Для отсутствующей строки при положительной дельте используется `INSERT … ON CONFLICT DO UPDATE`. Доказательство — 40 параллельных списаний по 1 шт. при остатке 10: ровно 10 успехов и 30 `409`, итог 0. Минус: часть логики живёт в SQL, поэтому `StockLevel` — это маппинг для схемы, а не объект, который грузят через UnitOfWork.

## 3. Что произойдёт, если Redis упадёт? Чем вы это проверяли?

Политика явная: чтение уходит в PostgreSQL, обычные записи проходят (инвалидация пропускается, TTL ограничивает устаревание), rate limiting и brute-force guard — fail-open, запросы с `Idempotency-Key` — fail-closed (`503`), потому что тихий дубль хуже повтора. Реально остановив Redis под работающим контейнером, я нашёл две проблемы: (1) phpredis 6 по умолчанию делает 10 ретраев с backoff — первая команда после обрыва висела ~39 с (решение: `OPT_MAX_RETRIES=0` в `FailFastRedis`); (2) мёртвый handle не восстанавливается сам, а адаптеры кэша Symfony глотают ошибки подключения, так что исключений для подсчёта нет. Поэтому `RedisCircuitBreaker` активно пингует Redis (раз в 2 с в норме, раз в 5 с при сбое), хранит состояние в APCu и переоткрывает соединение каждого воркера один раз за «поколение» сбоя. Результат: во время простоя ~5 мс на запрос, после возврата Redis всё включается само. Это покрыто функциональными тестами `RedisOutageTest`.

## 4. Как устроена инвалидация кэша и где она может дать устаревшие данные?

Cache-Aside поверх `RedisTagAwareAdapter`: запись → коммит в БД → `invalidateTags()`. Матрица «операция → теги» лежит в `CacheTags` и README. Теги бывают статическими (`product.<id>`, `merchant.<m>.products`) и выводимыми из загруженного значения (вид остатков получает `warehouse.<id>` для каждого склада, поэтому переименование склада обновляет все такие виды). Окна устаревания: (а) между коммитом и инвалидацией читатель может положить в кэш старое значение — ограничено TTL; (б) если Redis недоступен во время записи, инвалидация пропускается, записи живут до TTL (≤ 10 мин). Для защиты от stampede используется встроенный `get()` с блокировкой и probabilistic early expiration. Осознанный компромисс: изменение цены инвалидирует весь тег списка товаров мерчанта — просто и всегда корректно; при очень частых записях выгоднее ключи-версии.

## 5. Как вы защищаетесь от brute-force и почему не блокируете по ключу?

Отдельный `fixed_window` limiter считает только неудачные аутентификации по IP (10 за 15 минут). Guard сначала «подглядывает» через `consume(0)` и блокирует до любого поиска ключа, а токен тратит только после отклонённых учётных данных — легитимные клиенты бюджет не трогают. Верификация ключа выполняется за постоянное время (HMAC с pepper, `hash_equals`, хеш считается даже для неизвестного префикса — нет оракула существования ключа). Блокировка по ключу позволила бы атакующему заблокировать мерчанта (DoS), а при секрете в 192 бита подбор и так нереален — guard это defence in depth и защита от нагрузки на БД/кэш. Недостаток: клиенты за общим NAT делят бюджет; описано в «Known limitations».

## Бонус: как бы вы масштабировали это до 10× нагрузки?

Воркеры stateless → горизонтально. Горячий путь без БД: идентичность и каталог в Redis. Дальше: read-replica для cache-miss, Redis Sentinel/Cluster, версия-ключи вместо тегов списка, идемпотентность в БД в одной транзакции с операцией, лимиты на уровне API-gateway, метрики hit-ratio/латентности и алерты по состоянию breaker.
